# Release Process and Versioning

This guide defines the versioning scheme, changelog conventions, and release workflow for Lernza. It is intended for maintainers who are preparing a new release.

---
## 1. Versioning Scheme

We follow **Semantic Versioning 2.0.0** (SemVer):
- **MAJOR** – Incompatible API changes (e.g., breaking contract ABI changes, frontend major architecture rewrite).
- **MINOR** – Backwards‑compatible functionality added (new contract functions, new UI features).
- **PATCH** – Backwards‑compatible bug fixes.

Version numbers are expressed as `vMAJOR.MINOR.PATCH` (e.g., `v1.4.2`). All release tags in Git use this exact format.

---
## 2. Changelog Format

We use the **Keep a Changelog** style. The file lives at the repository root as `CHANGELOG.md`.

### Section headings
- `## [Unreleased]` – Drafted changes not yet released.
- `## [vX.Y.Z] - YYYY‑MM‑DD` – Published release.

### Entry categories
- `### Added` – New features.
- `### Changed` – Modifications to existing features.
- `### Fixed` – Bug fixes.
- `### Deprecated` – Features slated for removal.
- `### Removed` – Deprecated features that have been removed.
- `### Security` – Security‑related changes.

Each entry should reference the related issue/PR, e.g., `#123`.

---
## 3. Release Automation (release‑please)

The project uses the **release‑please** bot (see `release-please-config.json`). It automates:
1. Determining the next version based on Conventional Commits.
2. Generating a changelog entry.
3. Creating a Git tag and GitHub Release.

### How to trigger a release
- Merge all changes into `main` with **Conventional Commit** messages.
- Ensure the CI pipeline passes.
- The bot will open a PR titled `chore: release X.Y.Z`. Review, merge, and the release will be published.

---
## 4. Manual Release Checklist (if you need to release without the bot)
1. **Update version** in `package.json` (frontend) and `Cargo.toml` (contracts) to the new SemVer.
2. **Generate changelog**:
   ```bash
   npx -y release-please changelog --release-as=vX.Y.Z
   ```
3. **Commit version bump and changelog**.
4. **Tag the commit**:
   ```bash
   git tag -a vX.Y.Z -m "Release vX.Y.Z"
   git push origin vX.Y.Z
   ```
5. **Publish frontend assets** (if applicable):
   ```bash
   cd frontend
   pnpm build
   # Deploy built assets to your hosting (e.g., Vercel, Netlify)
   ```
6. **Publish contract WASM** to a public bucket or release asset.
7. **Announce** the release in the community channels and update the `README.md` badge.

---
## 5. Contributor Acknowledgement

The release notes automatically include a **Contributors** section generated by `release‑please`. It lists all authors of merged PRs for that release.

---
## 6. Hotfix Procedure

If a critical issue is discovered after a release:
1. Create a hotfix branch from the released tag (`vX.Y.Z`).
2. Apply the fix and increment the **PATCH** version (e.g., `vX.Y.Z+1`).
3. Follow the normal release steps.
